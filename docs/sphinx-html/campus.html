campus.constants module¶

Named constants for FixIt Campus: rules, roles, statuses and messages.

Every value is immutable (str, int or tuple) so no module can change it.

User-facing messages come from three sources:

  • Copied word for word from SRS FR-01: MSG_ID_NOT_FOUND, MSG_ALREADY_REGISTERED, MSG_PASSWORD_TOO_SHORT, MSG_NO_CONTACT_DETAILS and MSG_TOO_MANY_REQUESTS.

  • Copied word for word from SRS FR-02 to FR-04: MSG_INVALID_LOGIN, MSG_ACCOUNT_LOCKED, MSG_ACCOUNT_NO_LONGER_ACTIVE, MSG_NOT_AUTHORIZED, MSG_SESSION_EXPIRED and MSG_RESET_OTP_SENT.

  • From the UI design: MSG_OTP_INCORRECT and MSG_OTP_NO_LONGER_VALID.

  • Our own wording: MSG_OTP_EXPIRED, MSG_OTP_FORMAT, MSG_NEW_OTP_SENT and MSG_PASSWORD_CHANGED.

The UI-design and own-wording messages have not been checked against the SRS Wiki yet.

campus.forms module¶

Forms that check the SHAPE of user input (Presentation layer).

Forms check only that fields are present and well formed. Business rules, such as the minimum password length, live in services.py.

The complaint forms check that a photo is really a small JPG or PNG file and that the chosen location is one of the university’s locations, because both need only the input and the lists in constants.py.

campus.middleware module¶

Ends the session of a user who has been inactive too long (FR-03, NFR-07).

Part of the Presentation layer: it works only with the request and the session, so it imports nothing from the project except constants.

class campus.middleware.IdleTimeoutMiddleware(get_response: Callable[[HttpRequest], HttpResponse])[source]¶

Bases: object

Log out a user whose last request was too long ago.

The time of each request by a logged-in user is kept in the session. It is saved AFTER the view runs, so the login request itself is stamped. Must come after the session, authentication and message middleware in settings.MIDDLEWARE.

campus.services module¶

Business rules for FixIt Campus (Application layer).

This module holds the rules for FR-01 (register with OTP verification), FR-02 (log in, account lock, IUB records check), FR-04 (reset password), FR-06 to FR-08 (submit a complaint, find similar ones, follow), FR-09 (track complaints), FR-10 (reopen), FR-21 (browse complaints) and the staff actions FR-11 to FR-14 and FR-20 (filter, accept, resolve, location history, reject). FR-03 (log out, idle timeout) only changes the session, so it lives in the Presentation layer. This module never sees the request, the session or HTML. Outside systems are used only through records.py (university records) and delivery.py (sending the OTP).

Accept an Open complaint: it becomes In Progress and the user’s (FR-12).

The change runs in one transaction with select_for_update, so two staff members who press Accept at the same moment cannot both get the complaint. On databases that support row locks (for example PostgreSQL) the row is locked; SQLite has no row locks and serialises the writes instead, which gives the same result for this project.

  • complaint_id – The complaint ID.

Raises:

campus.services.log_in_user(id_number: str, password: str) → User[source]¶

Check the ID and password and return the user who may log in (FR-02).

The checks run in a fixed order: unknown or pending ID, lock, password, then the IUB records. The records are asked only after the correct password, so a wrong password never reveals whether a member has left. Starting the session is the view’s job.

No transaction.atomic() is used here on purpose: a wrong password must stay counted even though an error is raised afterwards.

Parameters:

  • id_number – The IUB ID number typed by the user.

  • password – The password typed by the user.

Returns:

The user, with the name and role copied from the records and the wrong-password count cleared.

Raises:

ServiceError – If the ID or password is wrong, the account is locked, or the ID is no longer in the records.
